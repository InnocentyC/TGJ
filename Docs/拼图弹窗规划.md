# 拼图弹窗功能规划

> 状态：代码已实现（步骤 1~5 完成），UI 预制体与 Unity 侧配置待搭建
> 范围：跳过对话逻辑，先以"背包接口"为前提完成拼图弹窗功能（收集记录 → 弹窗查看 → 拖拽吸附 → 拼完弹窗 → 跳音游）

---

## 一、目标流程

```
探索场景中收集碎片（对话侧，本期跳过，只留接口）
        │  调用背包接口记录
        ▼
随时点开拼图弹窗（每章独立预制体）
        │  按收集顺序在待摆放区生成已收集的碎片
        ▼
拖拽碎片 → 吸附到正确槽位（现有代码已支持）
        ▼
全部拼对 → 碎片淡出 → 结果图演出（现有 PuzzleManager 已支持）
        ▼
弹出"拼图完成"确认弹窗 → 点按钮 → 调 NotifyPuzzleCompleted() → 切音游场景
```

- 一共 **4 章**（ActCount 由 3 改 4 的场景操作由用户自己在 Unity 里做，代码按章节数据驱动，不写死章节数）。
- 拼图是探索场景内的弹窗，不单独切场景（`GameFlowConfig.puzzleScene` 留空即复用探索场景）。

---

## 二、现状盘点

### 已有、基本可用的（借来的拼图三件套）

| 文件 | 现有能力 | 需要的改动 |
|---|---|---|
| `CustomPuzzleImage.cs` | 拖拽跟手、吸附判定（最近空槽 + 距离 + 编号匹配）、失败弹回原位、CanvasGroup 淡出 | 中改：①去掉 `FindObjectOfType<PuzzleManager>` 的场景查找，改为由弹窗注入引用；②吸附成功后**锁定不可再拖** |
| `CustomPuzzleSlot.cs` | 记录放置、判对错、底图显隐 | 基本不动 |
| `PuzzleManager.cs` | 全量扫描槽位判完成、碎片淡出→结果图淡入、点图切换、完成/最后一张点击事件 | 中改：`totalPieces` 从配置读；支持弹窗动态生成的碎片注册 |

### 已有、直接对接的（架构侧）

- `GameProgressManager`：单例 + 存档，`ChapterProgress` 有 `puzzleCleared`；**`NotifyPuzzleCompleted()` 已实现**"拼图→音游"的推进，拼完弹窗的按钮直接调它即可。
- `GameFlowConfig`：`puzzleScene` 留空 = 拼图弹窗复用探索场景，符合设计；音游跳转走 `rhythmScene`。
- `WalkingSceneUI` + `PopupPanel`：弹窗懒加载/互斥框架现成，拼图弹窗继承 `PopupPanel` 走这条路。

### 缺失的（本规划要补的）

1. **背包接口**：没有"哪块碎片被收集了"的记录。
2. **每章拼图配置**：没有定义每章有哪些碎块、对应图、结果图。
3. **弹窗控制器**：没有按背包数据动态生成碎片的逻辑（借来的代码假设碎片开局全摆在场景里）。
4. **完成确认弹窗**：没有"拼完→点击→跳音游"的中间弹窗。

## 三、数据结构设计

### 核心原则：两层分离

| 层 | 内容 | 载体 | 特点 |
|---|---|---|---|
| **配置层** | 每章"有哪些块、谁对哪个槽、结果图" | ScriptableObject（每章一个 asset） | 静态，策划在 Inspector 里维护 |
| **运行层** | 玩家"收集了哪些块、收集顺序" | 存档（ChapterProgress） | 动态，随游戏进度落盘 |

**碎片不做成一个个独立物体**：碎片本体 = 一个通用碎片预制体模板，sprite / 编号由配置注入。`pieceIndex` = 配置列表序号，槽位按序号一一对应（0 号碎片 → 0 号槽）。

### 1. 配置层：`PuzzleChapterConfig`（ScriptableObject，新建）

```csharp
[CreateAssetMenu(menuName = "Puzzle/PuzzleChapterConfig")]
public class PuzzleChapterConfig : ScriptableObject
{
    [Serializable]
    public class PieceDefinition
    {
        public Sprite image;     // 碎片图案（必填）
        // pieceIndex 不存：直接用列表序号
        // correctSlotIndex 暂不加：默认槽位按序号一一对应
        //   若某章需要乱序对应，再补此字段（碎片身上的值由配置注入）
    }

    public PieceDefinition[] pieces;   // 数量不定，加一块就是加一项；总块数 = Length
    public Sprite[] resultImages;      // 拼完后的结果图（可多张，点着看）
    public GameObject pieceTemplate;   // 碎片预制体模板（带 CustomPuzzleImage）
    public GameObject completionPopup; // 拼完后的确认弹窗预制体（可选，留空走默认）
}
```

### 2. 运行层：背包接口（改造现有存档）

`GameFlowTypes.cs` 的 `ChapterProgress` 增加：

```csharp
public List<int> collectedPieceOrder;  // 按收集先后记录碎片编号（序号即配置列表索引）
```

> JsonUtility 支持 `List<int>`，旧存档该字段缺省为 null，读取后需要补空数组兼容。

`GameProgressManager` 增加（这就是对话系统将来要调的"背包接口"）：

```csharp
// 收集一块碎片（追加到该章收集顺序末尾）；重复收集返回 false
public bool CollectPiece(int actIndex, int pieceIndex);

// 查询
public bool HasPiece(int actIndex, int pieceIndex);
public IReadOnlyList<int> GetCollectedPieces(int actIndex);  // 收集顺序
public int GetCollectedCount(int actIndex);

// 拼图完成后由完成弹窗调用（已有的接口，不改）
public void NotifyPuzzleCompleted();
```

收集动作内部调用 `SaveProgress()` 落盘。

### 3. 章节注册：不做全局目录

每章独立弹窗预制体，**预制体自带自己那章的 `PuzzleChapterConfig` 引用**；探索场景的 `WalkingSceneUI` 只引用自己那章的弹窗预制体。加一章 = 加 prefab + 加 config asset + 场景里挂引用，互不干扰。暂不做集中注册表（以后做"拼图总览"界面再说）。

## 四、模块改造明细

### 4.1 新建：`PuzzlePopupController : PopupPanel`

挂在每个拼图弹窗预制体根节点上（和 `PopupPanel` 同一物体，直接继承它）。

字段：
- `PuzzleChapterConfig config`（拖本章配置）
- `Transform trayRoot`（待摆放区容器，挂 LayoutGroup 自动排序）
- `Transform boardRoot`（拼图板容器，槽位预摆在预制体里）
- `PuzzleManager puzzleManager`（同物体或子物体上）

`Show()` 重写逻辑：
1. 读 `GameProgressManager.Instance.ActIndex` 得当前章节（**弹窗预制体在哪个探索场景就对应哪章，取的是当前进度里的章**）。
2. 按 `GetCollectedPieces(actIndex)` 的顺序，把**尚未吸附到槽位**的碎片 `Instantiate(config.pieceTemplate, trayRoot)`，注入 sprite 和 `pieceIndex`；已吸附的碎片不动，保持挂在槽位上（**关闭弹窗后摆放进度保留**）。
   - 已吸附的判定：碎片身上有 `IsLocked` 标记（见 4.3），生成前先检查弹窗实例里已有的碎片，避免重复生成。
3. 未收集的碎片不生成（槽位保持空底框，玩家能看出"还缺哪块"）。
4. 把生成的碎片列表和 `config.pieces.Length` 注册给 `PuzzleManager`。

> 弹窗实例是懒加载复用的，`Hide()` 只做 `SetActive(false)`，所以槽位上的碎片和托盘里的碎片在本次场景内**天然保留**，无需额外存储。场景重载（存档续玩）后拼图从头开始——中途摆放状态不落盘，当前先接受这个行为。

`Hide()` 重写逻辑：
- 不做任何复位，直接隐藏（保留摆放进度）。

### 4.2 改造：`PuzzleManager`

- 新增 `Setup(PuzzleChapterConfig config, List<CustomPuzzleImage> pieces)`：设置 `totalPieces = config.pieces.Length`、注入结果图、登记碎片列表。
- `CheckPuzzleCompletion()` / `ResetPuzzle()` 里的 `FindObjectsOfType` 扫描改为遍历注册的碎片/槽位列表（避免扫到场景里其他物体，也去掉每帧全场景搜索的开销）。
- `ResetPuzzle()` 降级为调试用途（正常流程不再调用，因为关闭弹窗要保留摆放进度）。
- 淡出结果图演出、点图切换、`onPuzzleCompleted` / `onLastImageClicked` 事件逻辑**不动**。

### 4.3 改造：`CustomPuzzleImage`

- `puzzleManager` 引用改为公开的 `Setup` 注入（弹窗生成碎片时赋值），删掉 `Awake` 里的 `FindObjectOfType`。
- `FindClosestSlot` 的槽位列表来源改为注入的槽位数组（同一弹窗预制体），不再全场景搜索。
- **吸附成功后锁定**：`OnEndDrag` 吸附成功的分支里置 `isLocked = true` 并加公开只读属性 `IsLocked`；`OnBeginDrag` 开头检查 `IsLocked`，已锁定直接 `return`（不拿起、不变半透明、不换父物体）。锁定的碎片从"可拖列表"里剔除，后续 Show 补生成时据此跳过。
- 其余拖拽/吸附/弹回逻辑不动。

### 4.4 新建：拼图完成确认弹窗（只写脚本，UI 用户在 Unity 里和美术一起拼）

- 我们只提供**触发与跳转脚本**：监听 `PuzzleManager.onPuzzleCompleted`（或 `onImageTransitionComplete`）→ 弹出确认弹窗；确认按钮 `OnClick` → `GameProgressManager.Instance.NotifyPuzzleCompleted()` → 自动 `SaveProgress` + 切到本章 `rhythmScene`（`GameFlowConfig` 里必须配好每章的 `rhythmScene`，没配只打日志不切场景——这是现有行为，注意测试时配好）。
- 界面布局、文案、美术表现全部由用户在 Unity 里搭预制体，脚本侧只暴露一个 `Open()` 入口和按钮回调约定。

### 4.5 已通关章节：可重进，拼图重新开始

- 章节选择允许重进已通关的章节（`GameProgressManager.StartChapter` 已支持）。重进 = 探索场景重载 = 拼图弹窗实例销毁重建 → **拼图自然从头开始**，不需要任何特殊代码。
- 弹窗永远只显示**当前章节**的拼图：每个探索场景对应一章、每章一个弹窗预制体，天然隔离，弹窗内部逻辑不做章号区分。
- 已通关章节重拼完成 → 照常弹确认弹窗 → `NotifyPuzzleCompleted()`（重复置 `puzzleCleared = true` 无副作用）→ 重新进本章音游，即天然支持重玩。

## 六、Unity 侧（用户手动，和美术一起拼）需要准备的东西

**所有界面（拼图弹窗本体、完成确认弹窗）的布局与美术都由用户在 Unity 里搭建，代码侧只提供脚本与挂载点约定。**

1. **碎片预制体模板**：一个 Image 物体挂 `CustomPuzzleImage` + CanvasGroup，做成 prefab，拖进每章 config 的 `pieceTemplate`。
2. **每章拼图弹窗预制体**：根节点挂 `PuzzlePopupController`（含 PopupPanel 行为），内部含托盘区（LayoutGroup）、拼图板（预摆好 N 个 `CustomPuzzleSlot`，slotIndex 按序）、`PuzzleManager`、结果图、关闭按钮；拖好本章 config 引用。
3. **每章 `PuzzleChapterConfig` asset**：Create → Puzzle/PuzzleChapterConfig，填碎块 sprite 列表（顺序 = 编号 = 槽位序号）和结果图。
4. **完成确认弹窗预制体**：美术+文案自定，确认按钮的 `OnClick` 在 Inspector 里绑脚本暴露的"进入音游"方法。
5. **探索场景**：`WalkingSceneUI.puzzlePopupPrefab` 拖本章弹窗预制体。
6. **GameFlowConfig**：每章 `rhythmScene` 配好（音游跳转依赖它）。
7. **测试用调试入口**（临时）：Inspector 右键 `GameProgressManager` 提供一个菜单或用 `AssumeStage`，手动收集几块碎片来测弹窗——具体形式实施时定。

## 七、已知风险 / 注意点

- **吸附判定已改为世界坐标 pivot 比较**：碎片与槽位父级不同、碎片大小不一都不影响判定；吸附距离 `snapDistance` 按 Canvas 缩放系数自动换算。碎片/槽位的 Pivot 与 Anchor 均设中心即可。**托盘和拼图板仍需同属一个 Canvas**（同 Canvas 内 scale 一致才保证距离换算准确）。
- **LayoutGroup 与初始位置**：碎片开局位置由 LayoutGroup 决定，现有代码延迟到首次拖动才记录原位（`SaveHomePosition`），这个设计正好适配托盘布局，不要改成 Awake 记录。
- **旧存档兼容**：`collectedPieceOrder` 新字段在旧档反序列化后为 null，读取路径必须补空。
- **摆放进度只存内存不落盘**：已吸附的碎片状态保留在复用的弹窗实例里（本次场景内有效）；场景重载（包括章节选择重进已通关章）后拼图从头开始——这正是"重进重新拼"的预期行为，无需额外处理。
- **锁定状态与补生成的一致性**：Show() 补生成碎片时必须跳过已锁定的编号，否则同一块会出现两份（一份锁在槽上、一份躺在托盘）。
- **章节数**：`GameRules.ActCount = 3` 与实际四章不符，代码侧按数据驱动不写死，但用户改 ActCount 和 GameFlowConfig.acts 时需同步（由用户在 Unity 里操作）。
